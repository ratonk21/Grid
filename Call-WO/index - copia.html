Descripción

Crea una orden de trabajo (Work Order, WO) para uno o más dispositivos del cliente. La WO se crea en estado new, con tipo restoration, severidad minor y automation_rule_id: 0 (creación manual, no generada por una regla de automatización). La respuesta devuelve la etiqueta visible en UbiVu (work_order_label, p. ej. WO-14) y el id numérico.

Método
POST
Ruta
https://api.ubicquia.com/api/work-orders
Autenticación
Authorization: Bearer <access_token>; el cliente API requiere permiso de gestión de órdenes de trabajo
Límite
25 dispositivos por orden de trabajo
Idempotencia
No. Cada llamada exitosa crea una WO nueva

Inicio rápido

  1. Obtén un tokenPOST al endpoint de token del realm ubivu-prd con client_id y client_secret (ver Autenticación). Exporta el access_token como UBI_TOKEN.
  2. Identifica el dispositivoToma el Node ID del nodo (16 caracteres hexadecimales, p. ej. 44179354ce28576f) desde UbiVu o desde POST /v2/nodes/light (ver Identificador del dispositivo).
  3. Crea la ordenEnvía el cuerpo con reason y device_id como arrays. Respuesta 200 con data.work_order_label.
curl
curl -X POST 'https://api.ubicquia.com/api/work-orders' \
  -H 'accept: */*' \
  -H "Authorization: Bearer $UBI_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "cell",
    "urgent": 0,
    "reason": ["Other"],
    "notes": "Work order created via API",
    "device_id": ["44179354ce28576f"]
  }'

Autenticación

OAuth2 con flujo client_credentials contra Keycloak (realm ubivu-prd). El access_token se envía en el header Authorization de todas las llamadas a api.ubicquia.com.

Token URL
POST https://auth.ubihub.ubicquia.com/auth/realms/ubivu-prd/protocol/openid-connect/token
Content-Type
application/x-www-form-urlencoded
Vigencia
expires_in en la respuesta (6 h en el entorno de referencia). Renovar antes del vencimiento; un token vencido responde 401
Parámetro (form)Valor
grant_typeclient_credentials
scopeopenid
client_idCliente API del cliente UbiVu
client_secretSecreto del cliente API
bash
# obtiene el token y lo deja en UBI_TOKEN (requiere jq)
export UBI_TOKEN=$(curl -s -X POST 'https://auth.ubihub.ubicquia.com/auth/realms/ubivu-prd/protocol/openid-connect/token' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'grant_type=client_credentials' \
  -d 'scope=openid' \
  -d "client_id=$UBI_CLIENT_ID" \
  -d "client_secret=$UBI_CLIENT_SECRET" | jq -r .access_token)

Gestión del cliente API (sección User del Swagger)

MétodoRutaUso
POST/generate-api-user-client-keycloakCrea el cliente API en Keycloak
GET/get-api-user-client-accessDevuelve client_id y client_secret
GET/v2/regenerate-client-secretRota el secreto (usar si se expuso un token o el secret)
DELETE/delete-api-user-client-keycloakElimina el cliente API
El token es un JWT: su payload (base64, no cifrado) expone client_id, roles e IP de origen. Trátalo como una credencial. Nunca lo incluyas en front-ends públicos; en integraciones web usa un backend o función serverless que guarde las credenciales.

Prueba de credenciales sin efectos. Un cuerpo vacío ({"reason":[],"device_id":[]}) responde 422 de validación cuando token y permisos son correctos, sin crear ninguna orden. Sirve para validar la integración antes de operar sobre dispositivos reales.

Identificador del dispositivo

device_id lleva el Node ID del dispositivo: 16 caracteres hexadecimales (formato EUI-64), el mismo identificador que usa el parámetro {dev_eui} en otros endpoints (/v2/notifications/{dev_eui}, /v2/thresholds/nodes/{dev_eui}).

IdentificadorEjemploUso en device_id
Node ID (dev_eui)44179354ce28576fsí
node_id de la respuesta35no — clave interna
Pole ID (activo)POLE-12345no — es la llave de apilamiento de la WO, no el dispositivo
IMEI / ICCID15–20 dígitosno documentado

Obtener los identificadores por API

curl
curl -X POST 'https://api.ubicquia.com/api/v2/nodes/light' \
  -H "Authorization: Bearer $UBI_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"filter": [], "page": 1, "per_page": 10000}'

Devuelve la lista de nodos de iluminación con identificadores (ID, dev_eui), ubicación y estado. Ajusta per_page si el cliente supera 10.000 nodos.

javascript
const payload = {
  type: "cell",
  urgent: 0,
  reason: ["Other"],
  notes: "Work order created via API",
  device_id: ["44179354ce28576f"]
};
const r = await fetch("https://api.ubicquia.com/api/work-orders", {
  method: "POST",
  headers: {
    "Authorization": "Bearer " + process.env.UBI_TOKEN,
    "Content-Type": "application/json",
    "accept": "*/*"
  },
  body: JSON.stringify(payload)
});
const j = await r.json();
if (r.status === 200) console.log("creada", j.data.work_order_label, j.data.id);
else console.error(r.status, j.message, j.errors || "");
Ejecutar desde servidor, script o función serverless. El endpoint no está pensado para llamadas directas desde el navegador (CORS) y el token no debe vivir en el cliente.
python
import os, requests

payload = {
    "type": "cell",
    "urgent": 0,
    "reason": ["Other"],
    "notes": "Work order created via API",
    "device_id": ["44179354ce28576f"],
}
r = requests.post(
    "https://api.ubicquia.com/api/work-orders",
    headers={
        "Authorization": f"Bearer {os.environ['UBI_TOKEN']}",
        "Content-Type": "application/json",
        "accept": "*/*",
    },
    json=payload,
    timeout=30,
)
j = r.json()
if r.status_code == 200:
    print("creada", j["data"]["work_order_label"], j["data"]["id"])
else:
    print(r.status_code, j.get("message"), j.get("errors"))

Construir request

Genera el cuerpo y el comando listos para pegar; con más de 25 dispositivos produce un lote por llamada. Se ejecuta en el navegador y no envía nada: el token se referencia como variable de entorno UBI_TOKEN.

Una o varias. Los valores por confirmar se advierten, no se bloquean.

Se quitan duplicados y espacios. Más de 25 → lotes automáticos.

Presiona Generar para ver el JSON, el curl, el fetch y el Python de cada lote.
